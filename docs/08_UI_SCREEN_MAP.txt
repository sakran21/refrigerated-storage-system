PROJECT: Refrigerated Storage Unit Rental System
DOCUMENT: UI Screen Map
VERSION: 0.1.0
STATUS: Locked UI Draft

==================================================
1. PURPOSE
==================================================

This document defines the screen structure for the Refrigerated Storage Unit Rental System.

This document defines:
- main navigation model
- Operator screens
- Admin screens
- shared screens
- record detail behavior
- notes behavior
- preview/confirmation flows
- tablet-first UI expectations

This document does not define final visual design, colors, CSS, or component code.

==================================================
2. UI DESIGN PRINCIPLES
==================================================

UI-001
The interface must be tablet-first.

UI-002
The primary target device is an Android tablet running Chrome.

UI-003
Desktop browser support is required.

UI-004
Phone-first layout is out of scope for v1.

UI-005
The interface must use dashboard tiles first, supported by a simple menu.

UI-006
The UI must avoid dense desktop-only layouts for Operator workflows.

UI-007
Daily Operator actions must be easy to reach from the dashboard.

UI-008
Admin oversight screens may contain denser tables and filters.

UI-009
Preview/confirmation screens must be used before costly or locked submissions.

UI-010
Locked records must clearly show that they cannot be edited by Operator.

UI-011
Admin-only functions must not appear as usable actions for Operator.

UI-012
Dev does not need a separate normal business UI in v1.

==================================================
5. NOTES UI RULES
==================================================

Notes are attached to individual records.

A record means one saved business object, such as:
- one customer
- one unit
- one rental
- one billing period
- one charge
- one payment
- one deposit credit
- one meter reading
- one review flag
- one audit log
- one system setting
- one admin correction

Notes may be blank at initial record creation.

Notes can be appended later.

List views must show notes as a normal column or compact summary beside other record fields.

Example list layout:
ID | Reading Value | Reading Date | Type | Notes

For records with multiple notes, list views should show:
- latest visible note summary
- note count
- truncated note preview

Full note history is visible from the individual record detail view.

Operator can append notes.

Operator cannot edit previous notes.

Operator cannot delete previous notes.

Admin can hide/manage notes.

Hidden notes are not visible to Operator.

Notes are never treated as a detached global notes page for normal Operator use.

==================================================

- billing/charge generation

- charge override
- charge void

- show calculated values
- show related customer/unit/rental context
- show warnings
- require explicit confirmation
- not save draft records

Submission screens must:
- require confirmed: true behavior in API
- create final locked record where applicable
- show success/failure result clearly

==================================================
25. ERROR AND VALIDATION UI
==================================================

Validation errors must be clear and close to the relevant field.

Common validation examples:
- required field missing
- meter reading values do not match
- payment amount must be positive
- unit is not available
- customer does not exist
- rental cannot close early
- confirmation required
- reason required for Admin correction
- Operator not authorized for action

Locked record messages must explain that the record cannot be edited through normal Operator workflow.
