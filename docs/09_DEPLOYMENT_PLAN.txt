PROJECT: Refrigerated Storage Unit Rental System
DOCUMENT: Deployment Plan
VERSION: 0.1.0
STATUS: Locked Deployment Draft

==================================================

1. PURPOSE
   ==================================================

This document defines the deployment plan for the Refrigerated Storage Unit Rental System.

This document defines:

* deployment environments
* hosting direction
* database deployment
* frontend deployment
* backend deployment
* GitHub repository rules
* secrets handling
* demo/showcase model
* production data rules
* backup expectations
* deployment workflow

==================================================
2. DEPLOYMENT PRINCIPLES
========================

DP-001
The system must be deployable as a real web application, not only as a local demo.

DP-002
The system must support local development before paid hosting is required.

DP-003
The deployed system must support tablet and desktop browser access.

DP-004
The deployed system must separate code, configuration, secrets, and production data.

DP-005
Production secrets must never be committed to GitHub.

DP-006
Production customer/payment/rental data must never be committed to GitHub.

DP-007
The public portfolio version must use fake seeded data only.

DP-008
The real production version must be private and separate from the public demo version.

DP-009
The application must be deployable from a GitHub-hosted monorepo.

DP-010
Deployment must remain simple enough for solo maintenance.

==================================================

==================================================
4. ENVIRONMENTS
===============

The project uses three practical environments:

1. Local Development
2. Public Demo
3. Private Production

==================================================
5. LOCAL DEVELOPMENT ENVIRONMENT
================================

Purpose:
Used for active development, testing, debugging, and feature implementation.

Runs on developer machine.

Local development includes:

* React frontend running locally
* ASP.NET Core backend running locally
* PostgreSQL database running locally
* development environment variables
* seeded fake development data

Local development must not require paid hosting.

Local development must not use real customer data.

Local development database may be reset during development.

Local development is used for:

* building features
* testing business rules
* testing API endpoints
* testing UI workflows
* testing database migrations
* debugging authentication
* preparing seeded demo data

==================================================
6. PUBLIC DEMO ENVIRONMENT
==========================

Purpose:
Used for portfolio, live demonstration, recruiter/employer review, and in-person showcase.

Public demo uses:

* deployed React frontend
* deployed ASP.NET Core backend
* deployed PostgreSQL database
* fake seeded data only
* demo login credentials

Public demo must not contain:

* real customer data
* real payment data
* real rental history
* real phone numbers
* real ID numbers
* real emergency contact information
* production secrets
* private client/business data

Public demo supports:

* Operator demo account
* Admin demo account

Demo accounts must use clearly fake credentials.

Example demo roles:

* demo_operator
* demo_admin

Public demo data must include realistic fake examples for:

* customers
* units
* active rentals
* closed rentals
* billing periods
* rent charges
* electricity charges
* payments
* deposit credits
* meter readings
* delinquent rentals
* notes
* review flags
* audit logs
* admin corrections
* system settings

Public demo must allow someone to understand the system without accessing private production data.

==================================================
7. PRIVATE PRODUCTION ENVIRONMENT
=================================

Purpose:
Used for the real business version of the application.

Private production uses:

* deployed React frontend
* deployed ASP.NET Core backend
* managed PostgreSQL database
* production environment variables
* real business data

Private production must be separate from public demo.

Private production must not share database with public demo.

Private production must not use public demo credentials.

Private production access is limited to:

* Operator account
* Admin account
* Dev account

Private production data must be protected from:

* public GitHub exposure
* demo environment exposure
* accidental seed overwrite
* local development reset scripts
* public screenshots containing real sensitive data

==================================================
8. HOSTING PROVIDER
===================

V1 hosting provider:

* Render

Render is used for:

* frontend static site
* backend web service
* managed PostgreSQL database

Reason:
Render keeps v1 deployment simple by allowing the frontend, backend, and database to live under one hosting provider.

Hosting budget target:

* $30 to $80 per month maximum operating comfort range

Paid hosting is not required at project start.

Paid always-on hosting becomes required when:

* the app is stable enough to showcase
* tablet access outside the developer machine is needed
* the backend must not sleep
* a public demo link is needed
* private production use begins

==================================================
10. BACKEND DEPLOYMENT
======================

Backend app:

* ASP.NET Core Web API
* C#

Deployment type:

* backend web service

Backend deployment must:

* connect to PostgreSQL
* run database migrations safely
* support cookie-based authentication
* support persistent sessions
* enforce role-based access control
* expose API endpoints to frontend
* restrict CORS to approved frontend origins
* read secrets from environment variables
* log application errors

Backend environment variables:

* database connection string
* authentication/cookie secret or data protection configuration
* ASP.NET Core environment
* allowed frontend origin
* demo seed mode flag where applicable
* logging level

Backend must not:

* hardcode secrets
* hardcode production connection strings
* expose stack traces to normal users in production
* allow public unauthenticated access to protected endpoints
* use local development database in deployed production

* accounts

* units
* rentals
* billing periods
* charges
* payments
* deposit credits
* meter readings
* notes

Database deployment must support:

* persistent storage

* backend code

==================================================
14. ENVIRONMENT VARIABLE RULES
==============================

Secrets and configuration must be stored outside source code.

Allowed in GitHub:

* `.env.example`
* placeholder values
* documentation explaining required variables

Not allowed in GitHub:

* real `.env`
* production connection strings
* production passwords
* cookie/auth secrets
* hosting tokens
* private credentials

Required backend configuration:

* DATABASE_URL or equivalent PostgreSQL connection string
* ASPNETCORE_ENVIRONMENT
* AUTH/COOKIE secret or data protection configuration
* ALLOWED_ORIGIN
* LOG_LEVEL

Required frontend configuration:

* API_BASE_URL
* ENVIRONMENT_NAME

==================================================
15. AUTHENTICATION DEPLOYMENT RULES
===================================

Authentication uses:

* ASP.NET Core cookie-based authentication
* persistent browser sessions
* role-based access control

Deployment must support:

* secure cookies in production
* correct frontend/backend origin configuration
* persistent login behavior
* logout behavior
* inactive account blocking

Production session behavior:

* users remain logged in until logout, expiration, or invalidation
* session cookies must not expose sensitive user data
* authentication must be enforced server-side

Demo environment:

* demo credentials are allowed
* demo accounts must not access production data

==================================================
16. BACKUP AND RECOVERY EXPECTATIONS
====================================

Production database must have a backup strategy before real business use.

Backup expectations:

* provider-managed backups where available
* manual export option before major changes
* migration caution before production updates
* ability to restore from recent backup

Before major deployment changes:

* confirm latest backup exists
* avoid destructive migrations without review
* test migrations locally first
* test migrations in demo before production where practical

Production data must not rely on a single local copy.

==================================================
17. DEPLOYMENT WORKFLOW
=======================

Standard workflow:

1. Develop locally
2. Run backend tests locally
3. Run frontend build locally
4. Run database migrations locally
5. Commit code to GitHub
6. Push to GitHub
7. Deploy to public demo environment
8. Test demo environment
9. Deploy to private production environment when applicable
10. Verify production health
11. Monitor logs after deployment

Production deployment must not be treated as complete until:

* frontend loads
* backend health check passes
* database connection works
* login works
* role access works
* core workflows work
* no obvious production errors appear in logs

==================================================
18. MIGRATION RULES
===================

Database migrations must be created through Entity Framework Core.

Migrations must be tested locally before deployed use.

Migration files may be committed to GitHub.

Production migration rules:

* avoid destructive schema changes without backup
* preserve financial/history data
* preserve audit logs
* preserve review flags
* preserve admin corrections
* preserve notes
* test major migrations in demo before production

Destructive changes to production data require explicit backup first.

==================================================
19. LOGGING AND MONITORING
==========================

Backend should log:

* application startup
* database connection failures
* authentication failures
* authorization failures
* API errors
* failed business rule validations
* failed correction actions
* failed charge generation
* failed meter reading submissions

Production logs must not expose:

* passwords
* full secrets
* database credentials
* sensitive customer identity data
* raw authentication cookies

Admin/business audit logs are stored in the database.

Technical application logs are handled by the hosting environment.

22. DEPLOYMENT PHASES
=====================

Phase 1:
Local development only.

Required before Phase 2:

* backend project exists
* frontend project exists
* local PostgreSQL works
* basic models exist
* authentication works locally
* core dashboard loads locally

Phase 2:
Public demo deployment.

Required:

* fake seed data
* deployed frontend
* deployed backend
* deployed demo database
* demo credentials
* basic workflows functional

Phase 3:
Private production deployment.

Required:

* stable core workflows
* production database
* private credentials
* production environment variables
* backup strategy
* no real data in GitHub
* no real data in public demo

Phase 4:
Operational maintenance.

Includes:

* bug fixes
* backups
* migration review
* logs review
* business rule adjustments
* security updates
* controlled deployment updates

==================================================
23. DEPLOYMENT SUCCESS CRITERIA
===============================

Deployment is successful when:

* public demo app loads from browser
* private production app loads from browser when applicable
* frontend connects to backend
* backend connects to PostgreSQL
* login works
* role access works
* Operator dashboard works
* Admin dashboard works
* database persists data after restart
* migrations are applied
* environment variables are not exposed
* GitHub contains no secrets
* GitHub contains no real business data
* demo app contains fake seeded data only
* production app is separate from demo app
* health endpoint works
* tablet browser can use core workflows
